- (decision) AD-1 [ADOPTED]: pnpm monorepo; applications deployables consume uniquement les API publiques des packages. Lie la direction apps -> screens -> domains -> core et empeche les dependances de packages vers apps.
- (decision) AD-2 [ADOPTED]: Next.js et Expo sont des shells de runtime, routing, providers et integrations de plateforme; les ecrans fonctionnels vivent dans packages/screens.
- (decision) AD-3 [ADOPTED]: un ecran est partage par defaut et ne depend ni de next/navigation ni d'expo-router; les variantes .native, .web, .ios et .android ne servent qu'aux differences de parcours, structure ou interaction.
- (decision) AD-4 [ADOPTED]: @project/ui est l'API UI du projet et l'unique package autorise a importer Tamagui; ecrans et UI de domaines n'utilisent que ses exports publics.
- (decision) AD-5 [ADOPTED]: packages/domains contient les regles et cas d'usage purs, avec ports de persistence et fournisseurs; il ne depend ni de Strapi, HTTP, PostgreSQL ni du rendu React.
- (decision) AD-6: apps/api est un runtime Strapi 5 avec PostgreSQL. Strapi possede le schema de persistence (content-types), le back office, les routes, policies, authentification et integrations; aucune dependance Strapi ne sort de apps/api.
- (decision) AD-7: chaque ecriture metier passe par une route de commande Strapi, un controller fin puis un use case de domaine; l'adapter Strapi mappe les entites et ports vers Document Service. Les endpoints CRUD generes sont reserves aux ressources editoriales explicitement exposees.
- (decision) AD-8: @project/api-client est le seul acces HTTP partage. Le contrat REST versionne est public, les DTO de transport ne sont ni les content-types Strapi ni les entites de domaine.
- (decision) AD-9 [ASSUMPTION]: Users & Permissions est l'identite des utilisateurs finaux avec la gestion JWT refresh de Strapi 5; les API tokens sont limites aux integrations serveur-a-serveur. Les policies Strapi effectuent l'autorisation de frontiere, les invariants et decisions metier restent dans les use cases.
- (decision) AD-10: les donnees historiques sont des snapshots explicites et les evenements metier sont persistants et internes en V1; aucune infrastructure event-driven distribuee n'est introduite.
- (question) A valider avant la premiere fonctionnalite: les utilisateurs finaux sont-ils tous geres par Users & Permissions, ou une identite externe doit-elle etre integree ?
- (question) A valider avant la premiere fonctionnalite: quels content-types sont editoriaux et quels aggregates transactionnels doivent interdire le CRUD Strapi public et le Content Manager ?
- (decision) AD-11: tout content-type est inscrit avant implementation dans un registre avec classification editorial, transactionnel ou historique, proprietaire, voies d'ecriture et permissions Content Manager. CRUD et ecriture CMS sont interdits par defaut pour transactionnel et historique.
- (decision) AD-12: chaque commande multi-ecritures declare son aggregate, sa cle de concurrence, ses snapshots et son evenement persistant. Son adapter utilise une transaction Strapi documentee ou echoue avant tout effet externe; les effets externes sont declenches apres commit par une strategie de reprise a decider.
- (decision) AD-13: infra est proprietaire des definitions d'environnements et de l'exploitation; avant toute production, un runbook dans infra attribue environnement, migration, sauvegarde, secret, promotion et rollback a un role responsable.
- (direction) AD-9 est corrige: le choix Users & Permissions et le mode JWT refresh restent une hypothese en documentation et ne lient pas le code avant la premiere capacite authentifiee.
- (version) PostgreSQL 18.6 est le baseline de developpement et CI, etabli par infra/compose.yaml et .github/workflows/ci.yml.
- (event) spine finalized; reviewer findings reconciled, deterministic lint passed, and repository checks passed
- (decision) AD-14 [ADOPTED]: configuration-as-code Strapi. Content-types, composants, routes, policies, permissions, roles, configurations fonctionnelles et donnees de reference sont declares et versionnes dans apps/api. L'interface d'administration ne constitue jamais une source de verite de configuration.
- (decision) AD-15 [ADOPTED]: la synchronisation de configuration Strapi est idempotente et s'execute dans un contexte de deploiement unique. Les secrets, tokens et valeurs propres a l'environnement sont injectes par variables d'environnement ou gestionnaire de secrets, jamais synchronises depuis le code.
- (decision) AD-15 precise [ADOPTED]: un job config-sync distinct, execute une fois avant les replicas API depuis la meme image, charge les manifests versionnes, prend un verrou PostgreSQL, converge les ressources gerees et echoue sur une derive non gerable. Le code est l'autorite des ressources gerees; aucune suppression n'est implicite.
- (direction) Le futur config-sync sera valide en CI sur une base vierge puis rejoue pour prouver son idempotence; les valeurs de secrets et par-environnement restent hors manifeste.
- (decision) AD-16 [ADOPTED]: les roles et permissions sont definis par manifests TypeScript metier. Roles referencent des capacites semantiques stables; un adapter apps/api est le seul code autorise a les traduire vers Users & Permissions et les policies Strapi. Chaque route exposee declare sa capacite; les controles de possession et invariants restent dans policy et use case.
- (decision) AD-17 [ADOPTED]: le contenu des content-types editoriaux explicitement autorises est administre dans l'interface Strapi et est exclu de config-sync. La parite inter-environnements porte sur configuration, roles, permissions et donnees de reference, pas sur ce contenu editorial mutable.
- (decision) AD-18 [ADOPTED]: config-sync cree et met a jour les donnees de reference gerees mais ne les supprime ni ne les archive implicitement. Tout retrait, remplacement ou archivage passe par une migration versionnee et explicite.
- (direction) Le starter pack est generique. Les noms de domaines et exemples tels que orders, products ou AMAP presentes dans la documentation sont illustratifs et ne prescrivent aucun modele metier.
- (decision) AD-19 [ADOPTED]: schema Strapi code-first avec migrations natives controlees. Toute transformation ou modification destructive est une migration versionnee testee sur une base precedente; deploiement unique, sauvegarde avant destruction et rollback uniquement par correction vers l'avant ou restauration. forceMigration false n'est pas un mecanisme de securite de production.
- (decision) AD-20 [ADOPTED]: les evolutions de schema sensibles suivent expand -> migrate -> contract; les migrations Strapi s'executant avant la synchronisation, elles utilisent prioritairement Knex contre l'ancien schema.
- (decision) AD-21 [ADOPTED]: les modules sont declares par un manifeste versionne; CI valide dependances, cycles, proprietes de ressources, routes, jobs et capacites avant que config-sync n'applique la composition au deploiement.
- (decision) AD-22 [ADOPTED]: chaque content-type, migration, donnee de reference, route, job et permission a un module proprietaire unique. Les autres modules consomment son API ou ses ports sans ecriture croisee directe.
- (decision) AD-23 [ADOPTED]: la desactivation normale retire acces, permissions et jobs tout en conservant les donnees. Toute desinstallation definitive suit un projet de migration explicite.
- (decision) AD-24 [ADOPTED]: un coeur RGPD reutilisable depend de ports de resolution, export et anonymisation des donnees personnelles; une extension Users & Permissions ne constitue qu'un adapter optionnel.
- (decision) AD-25 [ADOPTED]: un module devient plugin Strapi seulement apres preuve de reutilisation ou besoin explicite de distribution, API publique, configuration documentee, tests d'upgrade/desinstallation et absence de dependances aux content-types propres au premier projet.
- (decision) AD-26 [ADOPTED]: chaque produit deploie une image Strapi composee au build depuis son manifeste de modules. Le resolver valide et materialise uniquement les modules actifs et leur fermeture de dependances; un module inactif n'apparait ni dans l'image, ni dans les schemas, routes ou jobs charges. Tout changement de composition est un nouveau build et deploiement.
- (decision) AD-27 [ADOPTED]: les adaptations Strapi activables vivent dans des packages workspace sous modules/<module>. Chaque module declare cle, dependances et ressources possedees; le resolver materialise les modules actifs dans un repertoire de build Strapi genere. Ces modules ne sont pas des plugins Strapi publics par defaut.
- (decision) AD-28 [ADOPTED]: les modules declarent seulement les capacites qu'ils fournissent. Les roles et leur attribution sont definis uniquement dans le manifeste d'autorisation du produit et ne peuvent referencer que des capacites de modules actifs.
- (decision) AD-29 [ADOPTED]: le graphe de modules est compose uniquement de dependsOn obligatoires, transitifs et acycliques. Une integration optionnelle est un module-pont qui depend explicitement des deux modules integres; les dependances optionnelles dans un module sont interdites.
- (decision) AD-30 [ADOPTED]: les alternatives de fournisseur sont modelisees par slots d'exclusivite nommes. Les modules declarent les slots qu'ils fournissent; le resolver refuse plus d'un fournisseur actif par slot. Les conflits directs entre cles de modules sont interdits.
- (decision) AD-31 [ADOPTED]: les modules communiquent synchroniquement via contrats TypeScript publics et ports explicites, asynchroniquement via evenements metier persistants apres commit. Aucun module n'appelle strapi.service d'un autre module; HTTP est reserve aux systemes reels externes au deploiement.
- (decision) AD-32 [ADOPTED]: les evenements internes utilisent un outbox PostgreSQL transactionnel unique. La commande persiste evenement et etat metier dans la meme transaction; un worker separe livre au moins une fois apres commit. Les handlers sont idempotents, journalisent leur traitement, appliquent retry borne et placent les echecs finaux en echec operationnel. Aucun broker distribue en V1.
- (decision) AD-33 [ADOPTED]: le worker outbox est un service deploiement distinct de l'API HTTP, lance par une commande dediee depuis la meme image Strapi composee. API et worker partagent ainsi modules, contrats et version; leur scaling reste independant.
- (decision) AD-34 [ADOPTED]: plusieurs replicas worker reclament atomiquement des lots d'evenements PostgreSQL via verrou de lignes court et SKIP LOCKED, puis les traitent hors transaction. Chaque reclamation porte un bail expirant; un evenement non confirme redevient reclamable apres crash. Aucun verrou global ni verrou pendant appel externe.
- (decision) AD-35 [ADOPTED]: erreurs outbox permanentes echouent immediatement; erreurs transitoires ont au plus huit tentatives avec backoff exponentiel et jitter plafonne a une heure. Apres echec final, evenement failed alerte et rejouable seulement par action operationnelle explicite.
- (decision) AD-36 [ADOPTED]: l'exploitation outbox est vendor-neutral: logs JSON structures et metriques OpenTelemetry contenant evenement, handler, tentative et resultat; infra configure exporteurs et alertes. Une commande operateur versionnee inspecte et replanifie explicitement un evenement failed, sans contourner son handler.
- (decision) AD-37 [ADOPTED]: API REST en V1. Le build Strapi compose genere une specification OpenAPI 3.1 versionnee; @project/api-client est derive de cette specification et les tests de contrat verifient les routes et DTO, notamment personnalises. Le generateur Strapi experimental n'est pas l'unique garantie; exposition HTTP de la specification reste desactivee par defaut en production.
- (decision) AD-38 [ADOPTED]: endpoints produit sous /api/v1 des le premier contrat; changements compatibles dans la meme version, rupture sous /api/v2. Les versions coexistent jusqu'a une date de retrait documentee. Endpoints operationnels comme health restent hors version produit.
- (decision) AD-39 [ADOPTED]: succes REST sous enveloppe { data, meta? } alignee Strapi. Erreurs sous RFC 9457 Problem Details avec extension code applicative stable et erreurs de champs. L'adapter HTTP normalise les erreurs Strapi sans exposer leurs formes internes.
- (decision) AD-40 [ADOPTED]: collections produit paginees par curseur opaque avec limit et after. Le curseur encode un ordre stable propre a l'endpoint; meta porte le curseur suivant. Total absent par defaut et expose seulement si contractuellement justifie. Les limites et erreurs de curseur sont documentees par OpenAPI.
- (decision) AD-41 [ADOPTED]: chaque commande POST /api/v1 exige Idempotency-Key. Cle scopee par acteur et endpoint, liee au hash du payload et au resultat initial pendant 24 heures; meme cle et payload retourne ce resultat, meme cle et payload different retourne 409. Reservation, etat metier et outbox sont atomiques.
- (decision) AD-42 [ADOPTED]: Users & Permissions est le fournisseur identity-provider V1, derriere adapter Strapi. Sessions refresh avec access tokens courts; web utilise cookies HttpOnly securises et mobile stockage securise natif. API tokens exclusivement serveur-a-serveur. Configuration refresh, CORS et CSRF requises avec le premier parcours authentifie.
- (decision) AD-43 [ADOPTED]: autorisation en trois couches: Users & Permissions authentifie, policy Strapi verifie la capacite de route, cas d'usage recoit Actor independant et verifie possession, perimetre organisationnel et invariants. Les filtres client ne determinent jamais le perimetre d'acces.
- (decision) AD-44 [ADOPTED]: le starter V1 ne fixe aucun modele multi-tenant: aucun tenant, organization, relation obligatoire ni filtre global. Actor peut porter un scope futur; un produit multi-tenant devra choisir explicitement son isolation et adapter les modules concernes.
- (decision) AD-45 [ADOPTED]: tests par pyramide de composition: unitaires pour domaines purs; contrat de chaque module avec fermeture de dependances; integration Strapi/PostgreSQL pour chaque composition de reference. CI verifie resolver, config-sync vierge puis rejoue, migrations depuis version precedente et contrat OpenAPI/client, sans couvrir le produit cartesien des modules.
- (decision) AD-46 [ADOPTED]: compositions de reference CI: base sans module optionnel; fermeture de dependances de chaque module; fixture par module-pont et fournisseur de slot; composition par produit reel. Aucune composition full generique.
- (decision) AD-47 [ADOPTED]: livraison par promotion du meme digest d'image composee entre environnements, secrets externes. Ordre obligatoire: resolver/validation, build immuable, migration et synchronisation schema unique, config-sync, API HTTP et worker. Rollback code seulement schema compatible; sinon correctif vers avant ou restauration.
- (decision) AD-48 [ADOPTED]: environnements logiques local, ci ephemere, staging partage et production. Fournisseur cloud, reseau, sauvegardes et SLO restent differes jusqu'au premier produit deployable. La branche CI preprod existante devra etre mappee vers staging ou renommee.
- (decision) AD-49 [ADOPTED]: chaque runtime valide son environnement au demarrage; modules declarent seulement noms de variables requises et resolver les agrege. Infra injecte valeurs par gestionnaire de secrets. .env.example documente sans secret; aucun secret dans manifest, logs, OpenAPI ou config-sync.
- (decision) AD-50 [ADOPTED]: logger structure central dans chaque runtime, avec correlationId, traceId, module, operation, outcome et code erreur. Payloads, tokens, cookies et donnees personnelles interdits dans les logs; redaction centralisee. Audit metier dans evenements persistants, jamais seulement dans logs.
- (decision) AD-51 [ADOPTED]: Strapi Media Library et Upload gerent metadonnees et interface; un module fournisseur remplit slot object-storage. Fichiers prives par defaut; acces public ou URL signee seulement si content-type et cas d'usage l'autorisent explicitement. Autorisation upload et consultation applique AD-43.
- (decision) AD-52 [ADOPTED]: modules declarent jobs et horaires en code; scheduler dedie depuis meme image coordonne declenchements via PostgreSQL. Workers executent avec bail et idempotence. strapi.cron en memoire interdit pour jobs produit; horaires en UTC sauf besoin explicite de fuseau metier.
- (decision) AD-53 [ADOPTED]: notifications par ports: modules emettent intentions ou evenements, module notification les traite via outbox et persiste suivi livraison. Fournisseurs derriere slots email-provider, sms-provider, push-provider; domaines n'importent jamais SDK fournisseur. Retries, audit et secrets suivent AD-32, AD-36, AD-49.
- (decision) AD-54 [ADOPTED]: templates notification: content-type Strapi editorial gere sujet, corps, locale et variantes modifiables UI; module notification versionne cles stables, canaux autorises et schemas de variables. config-sync ne reecrit jamais contenu; rendu valide cle, canal et variables avant livraison.
- (decision) AD-55 [ADOPTED]: i18n opt-in par content-type editorial; manifeste produit definit locales BCP 47 et locale par defaut, config-sync les converge. Traductions gerees dans Strapi avec fallback explicite locale par defaut. Transactions, snapshots et evenements ne sont pas localises implicitement.
- (decision) AD-56 [ADOPTED]: cache explicite par endpoint. Ecritures et lectures authentifiees ou transactionnelles no-store; seules lectures editoriales publiques declarent Cache-Control et ETag eventuel. Publication ou mutation editoriale emet evenement outbox pour invalider caches web/mobile concernes. Aucun fournisseur cache fixe maintenant.
- (decision) AD-57 [ADOPTED]: offline opt-in par produit ou module; aucune synchronisation locale implicite V1. Capacite offline declare stockage local, commandes idempotentes, strategie conflit, reprise et indicateurs UX de synchronisation; elle entre dans composition et tests de reference.
- (decision) AD-58 [ADOPTED]: web supporte versions courante et precedente majeure de Chrome, Edge, Firefox et Safari; mobile supporte versions iOS/Android encore supportees par Expo SDK verrouille. Aucun navigateur ou OS legacy sans exigence produit explicite.
- (decision) AD-59 [ADOPTED]: objectif WCAG 2.2 AA web et semantique native equivalente Expo. @project/ui porte roles, focus, contraste et primitives accessibles; ecrans verifient clavier, lecteur ecran, libelles et retours etat. Variantes plateforme preservent equivalence accessible.
- (decision) AD-60 [ADOPTED]: garde-fous performance V1: pagination bornee, aucun populate Strapi non borne, aucun appel fournisseur synchrone dans commande, detection N+1. Budgets chiffres web, API, worker et base obligatoires par produit avant production; aucun SLO global arbitraire.
- (decision) AD-61 [ADOPTED]: defense frontiere explicite: routes non publiques par defaut; CORS allowlist injectee sans wildcard credentials; CSP web stricte et exceptions versionnees; rate limiting endpoints publics, auth et commandes via dependance partagee multi-replicas, seuils declares endpoint et fournisseur differe.
- (decision) AD-62 [ADOPTED]: ADR versionnee pour changement contrat public, slot, dependance module, securite, persistence ou deploiement. Deprecation annoncee contrat et maintenue au moins une release produit avant retrait; rupture accompagne migration, tests composition et mise a jour OpenAPI/client. Evolutions internes sans ADR.
- (direction) AD-4 precise [ADOPTED]: packages/ui et packages/screens ne contiennent aucun element JSX HTML intrinseque. packages/ui est seul autorise a importer Tamagui; packages/screens consomme exclusivement @project/ui. Le controle lint verifie les elements JSX HTML dans ces packages.
